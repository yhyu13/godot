# DOC_SPEC — Godot 模块教学文档写作规范

> 本规范是每个模块文档（`docs/<层>/<模块名>.md`）的唯一写作契约。调度 agent 必须逐条遵守。面向对象是「想读懂 Godot 引擎内部的人」，不是查 API 手册的人。

## 0. 硬性纪律（先读，违反即返工）

1. **结论先行**：每个模块文档第一段就写一句加粗结论——这个模块「干什么、为谁服务、代价是什么」。不要铺垫。
2. **源头锚定**：每个判断、每个类名、每个 API 都要钉到真实文件（`文件:行号` 或 `文件路径`）。**禁止编造不存在的类名 / API / 函数**——写完前用 grep 确认符号真实存在。
3. **说人话，去 AI 味**：先比喻后术语。删掉「值得注意的是 / 综上所述 / 赋能 / 抓手」这类套话。一段一个意思。
4. **数字带参照物**：说「大」就给量级（文件数、代码行数、注册的类数量），不写「很大/很多」。
5. **对比句 ≤3 处**；核心观点全文只出现 2 次（定义处 + 总结处）。
6. **只写这个模块**：不顺手扩展相邻模块，不写「未来可能用到」。

## 1. 每个模块文档的固定结构（8 段）

```markdown
# <模块名>（<层>）

> 一句话：<讲人话的比喻 + 术语>。

**结论**：<这个模块干什么、为谁服务、代价是什么，一句加粗。>

## 是什么 / 不是什么
<钉概念：对比句 ≤3 处。它负责什么，不负责什么（不负责的交给谁）。>

## 在引擎里的位置
<一张 mermaid flowchart，画它依赖谁、被谁依赖。>

## 关键概念
<2-5 个概念，每个 = 一句比喻 + 术语 + 一个真实类名锚点。>

## 核心文件（按阅读顺序）
1. `<path/file.h>` — <这个文件干什么，1 行。>
2. ...

## 数据流 / 调用链
<一张 mermaid（flowchart 或 sequenceDiagram），画一次典型调用。>

## 中文口诀
<4-8 句顺口溜，帮助记住这个模块的主干。>

## 练习（15 分钟）
1. <具体可操作的一步。>
2. ...

## 自测
- [ ] <一个能靠读代码回答的问题。>

## 一句话总结
> <这个模块的定位，一句话收束。>
```

## 2. 怎么写（操作步骤）

1. 从 `docs/INDEX.md` 认领一个 `- [ ]`，改成 `- [~]`。
2. 用 `ls` / glob 列出该模块源目录（如 `core/math/`、`modules/gdscript/`、`servers/rendering/`）。
3. 找「入口」：读 `SCsub`（若有）看它编译哪些文件；读 `register_types.cpp` / `register_types.h`（若有）看它注册了什么类。
4. 只读关键 `.h`（公共接口）和少量 `.cpp`，不逐行读源码。目标是「讲清主干」，不是「穷举实现」。
5. 按第 1 节模板写 `docs/<层>/<模块名>.md`，全中文。
6. 写完后把 `docs/INDEX.md` 里该项改成 `- [x]`。

## 3. 交付自检（写完必过）

- [ ] 结论在文档第一段（加粗）。
- [ ] 每个类名/API 都在源码里 grep 到过（不编造）。
- [ ] 至少 2 张 mermaid 图（位置图 + 数据流图）。
- [ ] 有「中文口诀」和「练习 / 自测」。
- [ ] 没有「值得注意的是 / 综上所述」这类套话。
- [ ] 没碰 `thirdparty/`，没写相邻模块。
- [ ] `docs/INDEX.md` 里该项已从 `[~]` 改成 `[x]`。

## 4. 覆盖状态约定（与 INDEX.md 同步）

- `- [ ]` 未覆盖
- `- [~]` 进行中（认领后、写完前）
- `- [x]` 已覆盖

**认领规则**：一次只认领一个 `- [ ]`，先改成 `- [~]` 再动手，防止并发重复。若发现所有项都不是 `- [ ]`（全是 `[~]` 或 `[x]`），返回 `ALL_COVERED` 停止。
